# Ограничения решения

## Поддерживаемые условия

| | |
|---|---|
| ОС | Android 9+ (minSdk 28), проверено на Android 15 |
| Процессор | только **arm64-v8a** (все современные телефоны) |
| Память | рекомендуется ≥ 4 ГБ ОЗУ: распознавание ~0.8 ГБ, LLM в отдельном процессе ещё ~1.9 ГБ (запускается только после расшифровки) |
| Место | APK ~1.36 ГБ (модели встроены по ТЗ) + ~1 ГБ копия LLM при первом конспекте + ~0.9 ГБ кэш LLM (системный кэш, Android может его очистить) |
| Язык | **русский** (GigaAM v3 обучена на русской речи) |
| Форматы | всё, что декодирует Android: wav, mp3, m4a/aac, ogg/opus, flac, 3gp, amr; любая частота и число каналов |
| Длительность | проверено до **52 мин** (созвон, WebM/Opus 48 кГц stereo, 6 участников). Аудио держится в памяти уже в 16 кГц моно (~4 МБ на минуту, пик при декодировании ×2), поэтому ~1 ч помещается в типичный лимит памяти приложения 512 МБ |
| Сеть | не нужна вообще, у приложения нет разрешения `INTERNET` |

## Известные ограничения

**Распознавание**
- Английский не поддерживается: GigaAM распознаёт только русский. Английские слова в русской речи распознаются
  «на слух» кириллицей или с ошибками.
- Тестовый набор синтетический (TTS). На живых записях с шумом, эхом, плохим микрофоном и перебиваниями WER будет выше.
- Декодирование Opus/Vorbis (WebM, Ogg) идёт программным кодеком Android пакетами по 20 мс и на длинных файлах
  заметно дольше WAV/MP3/AAC.
- Редкие имена и термины могут искажаться: словаря пользователя нет.

**Диаризация**
- Одно слово — один спикер: при одновременной речи (наложениях) слова отходят одному из говорящих.
- Очень быстрый обмен короткими репликами без пауз — самый трудный случай (DER 15 % на `piper_fast`).
- Реальный созвон (52 мин, сжатый звук, 5+ участников) делится хуже синтетики: ~⅓ смен спикера приходится
  на середину фразы (эталона нет, оценка по тексту). Параметры подобраны на синтетических диалогах.
- В режиме «Авто» очень похожие голоса могут слиться в одного спикера. Спикер, сказавший суммарно меньше ~3 с
  (или < 4 % записи), присоединяется к соседу, только если его голос похож на соседний. Порог слияния раздробленных
  голосов (0.9) подобран на одном реальном созвоне (6 участников; при 0.89 — 5, при 0.92 — 7–8), поэтому на других
  длинных записях число спикеров может отличаться на ±1. Если число участников известно, его можно указать вручную (1–6).
- **Имена** находятся только по тексту: обращения («Оля, ты с нами?») и самопредставления. Если по имени никого
  не звали, или голоса противоречат друг другу (часто на живых созвонах, где диаризация делит одного человека на
  несколько «спикеров»), остаётся «Спикер N». Неверное имя хуже его отсутствия, поэтому порог строгий.
  Ошибку ASR в имени («Мурка» → «Морка») приложение не исправляет. Имя можно задать вручную тапом по спикеру.
- В JSON-экспорте имён нет: `speaker_id` — строго `speaker_N`, как в ТЗ. Имена есть на экране, в TXT и в конспекте.

**Живой режим (во время записи)**
- Это предпросмотр: спикеры в живом режиме определяются онлайн (без «взгляда вперёд») и могут отличаться от итоговой
  расшифровки, которая делается после «Стоп» полным пайплайном.
- Итоговый текст фразы появляется после паузы; во время длинного монолога виден серый черновик (обновляется раз в ~2 с).
  На медленном телефоне (или в эмуляторе, свёрнутом за другими окнами) распознавание может отставать от речи —
  черновик тогда не строится, чтобы не отставать ещё больше.
- Имена в живом режиме ищет тот же алгоритм по тексту (`SpeakerNamer`), не LLM: LLM отнимала бы процессор у распознавания.
- В эмуляторе Android звуковой HAL иногда «теряет» микрофон через ~3 с после начала записи (ошибка `pcm_readi I/O error`,
  дальше только нули). Приложение замечает секунду цифровых нулей и само переоткрывает микрофон; пропуск заполняется
  тишиной, чтобы таймкоды не съехали. На телефонах такого не наблюдали.

**Таймкоды**
- Таймкоды — на уровне реплик (`start_ms`/`end_ms`), как в ТЗ; точность по нашим тестам ±50–230 мс.
  Подряд идущие фразы одного спикера с паузой < 1 с объединяются в одну реплику.
- Таймкоды слов (для подсветки при проигрывании) — из токенных таймкодов ASR, точность ~±0.1–0.3 с; у записей,
  расшифрованных до появления этой функции, слова распределены по реплике приблизительно.

**Локальная LLM (конспект)**
- Qwen3 1.7B — маленькая модель: конспект и ответы бывают общими или неточными (например, обещание приписано не тому
  участнику). Поэтому LLM **не изменяет** текст расшифровки, а под ответом на вопрос показывается цитата из расшифровки,
  проверенная программно, — по ней видно, на что опирался ответ.
- Контекст модели — 2048 токенов. Длинные записи обрабатываются по частям (map-reduce): 52-минутный созвон — 19 частей,
  ~3.5 мин на эмуляторе. Если во время конспекта начать новую расшифровку, конспект приостанавливается и потом
  начинается заново с первой части.
- Ответ на вопрос в эмуляторе — 30–60 с (на телефоне быстрее); для длинной записи модель видит не весь текст, а найденные
  по словам вопроса фрагменты, поэтому вопросы «своими словами» (без слов из разговора) отвечаются хуже.
- Первый конспект после установки дольше на несколько секунд: модель (~1 ГБ) копируется из APK во внутреннюю память.
- Работает на CPU. GPU — только запасной путь, если CPU-движок упал; на устройствах без OpenCL он недоступен.

**Размер**
- APK ~1.36 ГБ: так требует ТЗ (модели встроены). Отдельной «лёгкой» сборки с загрузкой моделей нет — это противоречило бы приватности.

**Часы (Wear OS)**
- Нужны часы Wear OS 3+ с Google Play Services, сопряжённые с телефоном. На телефоне — Крабер той же подписи
  (наши APK подписаны одним ключом). Часы без телефона не расшифровывают: модели живут только на телефоне.
- Поток — несжатый PCM 16 кГц (256 кбит/с): качество как у записи с телефона, но на слабом Bluetooth поток может
  отставать. Отставание буферизуется (до 2 мин); дальше — запись уйдёт целиком после «Стоп».
- Если Крабер на телефоне закрыт, система поднимает его сама, но Android не даёт запустить уведомление с прогрессом
  из фона; на практике приём надёжен, пока приложение открыто или недавно использовалось. Если поток не дошёл,
  запись всё равно придёт целиком повторной отправкой.
- Живой текст во время записи с часов виден только на телефоне (на часах — анимация и таймер).
- На эмуляторах без пары по Bluetooth проверяли через отладочный TCP-мост (тот же протокол); Bluetooth-путь — на реальных часах.

## Что не входит в текущую версию

- Узнавание человека по голосу между записями (enrollment): имена сейчас находятся только по тексту разговора.
- Экспорт в PDF/DOCX (есть JSON по ТЗ и TXT через «Поделиться»).
- Английский язык (нужна отдельная модель и переключатель).
- Любая синхронизация и облако.

## Риски демонстрации

| Риск | Что делаем |
|---|---|
| Слабый телефон эксперта (мало ОЗУ) | расшифровка работает и без LLM; если процесс LLM упадёт, текст и экспорт не пострадают, в карточке конспекта будет понятная ошибка |
| Мало места на телефоне (нужно ~3.3 ГБ с LLM) | установка APK требует ~1.4 ГБ; LLM копируется только при первом конспекте |
| Эмулятор на Mac M4/M5 | движок LLM падает (SIGILL) на SME-инструкциях: эмулятор сообщает, что поддерживает их, но выполнить не может. Лечится параметром AVD `kernel.parameters=arm64.nosme arm64.nosve`. Окно эмулятора должно быть видно, иначе macOS App Nap замедляет его в ~3 раза |
| AAC/MP3 на эмуляторе | программный декодер медленнее аппаратного (93 с m4a → 10.7 с декодирования); на телефоне быстрее |
| Шум в зале при записи с микрофона | для демо лучше импорт подготовленного файла; запись — второй сценарий |

## Дальнейшее развитие

1. Живой режим: потоковая модель (zipformer ru) для черновика вместо повторного распознавания GigaAM.
2. Enrollment голосов: эмбеддинг CAM++ по 10 с речи → имя вместо «Спикер N» во всех записях.
3. Часы: последняя фраза бегущей строкой на часах, кнопка «важный момент» с вибрацией, сжатие звука (Opus) для слабого Bluetooth.
4. Вопросы ко всем разговорам сразу («что мы решили по бюджету за месяц?») поверх текущего поиска.
5. Английский: вторая ASR-модель и автоопределение языка.
6. Ускорение: NNAPI/QNN для ASR, GPU для LLM на телефонах с OpenCL.
