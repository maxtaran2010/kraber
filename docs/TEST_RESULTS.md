# Методика и результаты тестирования

## Что проверяем

То же, что эксперты: импорт файла → обработка в приложении → экспорт JSON → сравнение с эталоном.

| Метрика | Как считаем (`tools/eval/eval.py`) |
|---|---|
| **WER** | по словам после нормализации: нижний регистр, без пунктуации, ё → е |
| **DER** | доля времени эталонной речи с ошибкой: пропуск + лишняя речь + путаница спикеров. Сетка 10 мс, **без «воротника»** (collar 0), спикеры сопоставляются жадно по пересечению. Это строже стандартного DER с collar 0.25 с |
| **Границы** | средняя ошибка `start_ms` / `end_ms` реплики эталона и ближайшей реплики гипотезы |
| **RTF** | время обработки / длительность аудио, от нажатия «Расшифровать» до готового текста. Конспект LLM не входит: он строится после, в фоне, и не блокирует экспорт |

## Тестовый набор

Настоящих «диалогов котиков» от организаторов до сдачи нет, поэтому набор сделан самостоятельно.
Он собирается скриптами и полностью воспроизводим:

- `piper_2spk`, `piper_3spk`, `piper_4spk` — диалоги на 2, 3 и 4 голоса (Piper TTS: denis, dmitri, irina, ruslan + macOS Milena),
  паузы и громкость случайны с фиксированным сидом (`tools/eval/make_piper_dialogs.py`);
- `piper_fast` — быстрая речь, короткие реплики, наложения;
- `piper_noisy.m4a` — тот же диалог, что `piper_3spk`, с фоновым шумом, перекодированный в AAC 44.1 кГц stereo
  (проверка декодера и ресемплера);
- `dialog1` — 3 «голоса» из одного macOS-голоса сдвигом высоты тона (`tools/eval/make_test_dialog.py`).

Плюс ручные проверки: живая запись с микрофона в приложении (32 с, один человек, читает текст с экрана)
и записи с одним говорящим. Задача ручной проверки — убедиться, что текст не теряется, а одного человека
приложение не делит на нескольких.

> Ограничение набора: синтетическая речь чище и ровнее живой. На живых записях WER будет выше, особенно
> на шуме, перебиваниях и плохом микрофоне (`docs/LIMITATIONS.md`).

## Результаты в приложении

Сборка: debug-APK. Режим спикеров «Авто», никаких ручных настроек. Устройство — эмулятор Android 15 arm64
(4 ядра, 6 ГБ ОЗУ) на Apple M5 Pro. Прогон: `tools/eval/device_eval.sh <файлы>`. Сырые данные — `artifacts/test-results/results.csv`.

| Файл | Длит. | Спикеров (эталон / найдено) | WER | DER | Границы старт / конец | Обработка | RTF |
|---|---|---|---|---|---|---|---|
| piper_2spk | 72.5 с | 2 / 2 | 6.33 % | 4.01 % | ±432 / ±594 мс¹ | 6.1 с | 0.085 |
| piper_3spk | 93.2 с | 3 / 3 | **2.84 %** | 5.22 % | ±56 / ±139 мс | 4.3 с | **0.046** |
| piper_4spk | 113.6 с | 4 / 4 | 4.56 % | 5.06 % | ±49 / ±149 мс | 17.6 с² | 0.155² |
| piper_fast | 37.1 с | 3 / 3 | 12.79 % | 14.77 % | ±150 / ±228 мс | 6.5 с | 0.175 |
| piper_noisy.m4a | 93.2 с | 3 / 3 | 5.21 % | 6.78 % | ±49 / ±204 мс | 33.0 с³ | 0.354³ |
| dialog1 | 36.2 с | 3 / 3 | 4.84 % | 6.22 % | ±62 / ±146 мс | 5.3 с | 0.147 |

¹ В эталоне `piper_2spk` подряд идущие фразы одного спикера — отдельные реплики. Мы склеиваем их, если пауза меньше 1 с,
и метрика «ближайшая реплика» за это штрафует. Диаризация на этом файле при этом почти идеальна (DER 4 %).
² macOS App Nap замедляет эмулятор, когда его окно перекрыто другими: все этапы, включая VAD, медленнее в ~3 раза.
Прогоны с открытым окном: piper_3spk — 4.3 с, а с перекрытым — 12.6 с. На телефоне этого эффекта нет.
³ 10.7 с из 33 — декодирование AAC программным кодеком эмулятора. На телефоне AAC декодируется аппаратно.

**Итого:** число спикеров определено верно на всех 6 файлах. WER на обычной речи — 3–6 %, DER — 4–7 %.
Слабое место — очень быстрая речь с короткими репликами без пауз: WER 13 %, DER 15 %.

### Время по этапам (piper_3spk, 93 с аудио)

| Декодирование | VAD | Распознавание (GigaAM) | Диаризация (CAM++) | Всего |
|---|---|---|---|---|
| 0.08 с | 0.46 с | 2.10 с | 1.64 с | 4.3 с (RTF 0.046) |

Модель ASR загружается один раз при первой обработке (~2–3 с), дальше остаётся в памяти.

## Как менялось качество диаризации

| Вариант | dialog1 DER | piper_* DER |
|---|---|---|
| v1: pyannote-segmentation 3.0 → ASR по сегментам | 43 % (терялась речь) | — |
| sherpa-onnx `OfflineSpeakerDiarization` (pyannote + CAM++), подбор порога | 13–28 % | 13–28 % |
| **v2 (текущая): VAD → ASR → своя диаризация на CAM++ + AHC** | **6.2 %** | **4.0–6.8 %** (fast — 14.8 %) |

Параметры v2 подобраны перебором (`tools/eval/sweep.sh`) на Python-зеркале пайплайна (`tools/eval/proto_pipeline.py`),
затем перенесены в Kotlin. Результаты приложения совпадают с прототипом до сотых долей процента.

## Локальная LLM (конспект)

- Модель: Qwen3 1.7B int4 (LiteRT-LM, CPU). На эмуляторе: инициализация 1.2–3 с, конспект 6–11 с
  (без замедления App Nap). Конспект строится после расшифровки, когда очередь файлов пуста. Если пользователь
  импортирует следующий файл, конспект ставится на паузу и не замедляет распознавание.
- Сравнение с Qwen3 0.6B на тех же записях: у 0.6B названия и итоги заметно менее связные, 1.7B даёт осмысленные
  названия и итоги («Заседание Кошачьего комитета» → «Договорено на дежурство в подвале по графику и охрана дивана всеми»).
- Модель 1.7B выдумывала «задачи», которых в разговоре не было. Поэтому отдельного раздела задач нет:
  договорённости модель пишет отдельным пунктом, и только если в тексте есть слова-маркеры обещаний и сроков.
  Упоминания несуществующих спикеров отфильтровываются.

**Конспект v2: было → стало** (эмулятор, те же записи):

| Запись | Было | Стало |
|---|---|---|
| Приветствие (4 с, 4 слова) | «• Обмен приветствиями» — пустой конспект | только название «Приветствие», карточки конспекта нет |
| dialog1 (36 с) | два общих пункта | Суть «Обсуждение отчёта по запасам корма и планирование проверок» + 2 пункта; «✓ Барсик — проверит склад до пятницы» |
| piper_3spk (93 с) | 3 общих пункта | Суть + 5 конкретных пунктов (мыши в подвале, дежурство с понедельника, диван) + «Договорились» |
| Созвон «Оперконтур» (52 мин) | 3 общих пункта только по началу и концу (текст обрезался) | 19 частей хронологии 0:06–52:18 с переходом к месту + суть и пункты; ~3.4 мин без App Nap |

Ограничение модели: обещание иногда приписывается не тому участнику.

**Вопросы к разговору** (эмулятор):

| Запись | Вопрос | Ответ |
|---|---|---|
| dialog1 | Кто что пообещал? | «Барсик пообещал проверить склад … до пятницы» + цитата «Принято. Проверю до пятницы и пришлю отчёт.» — Барсик |
| dialog1 | Сколько стоит ремонт крыши? | «В записи об этом не говорили.» (без вызова модели, < 1 с) |
| piper_3spk | Что решили про диван? → «А почему?» | «Диван охраняем все вместе» → «Пёс не умеет ловить мышей» (уточняющий вопрос понят) |
| Оперконтур | Что говорили про кодировку? | Windows vs UTF-8 для казахских символов, с цитатой (поиск по фрагментам в 52-минутной записи) |

Время ответа на эмуляторе — 30–60 с; повторный вопрос быстрее (процесс модели остаётся «тёплым» 60 с).

## Имена спикеров

`SpeakerNamerTest` (JUnit, `./gradlew :app:testDebugUnitTest`) прогоняет реальный вывод приложения
(`.cache/test/*.dev.json`) против сценариев диалогов.

| Файл | Кто есть кто в сценарии | Найдено |
|---|---|---|
| piper_2spk | speaker_2 = Мурка | ✓ «Морка» (так распознал ASR) |
| piper_3spk, piper_noisy | speaker_2 = Мурка, speaker_3 = Васька | ✓ оба |
| dialog1 | speaker_3 = Барсик | ✓ |
| piper_4spk | Рыжик, Мурка, Соня — по имени зовут только Рыжика, а ASR услышал «Айжек» | — (без имён, без ошибок) |
| piper_fast | имён нет | — |

**Итого:** 6 имён из 9 возможных, **0 неверных**. Клички отсутствующих котов (Барсик, Рыжик, Пушок в 2spk — «в третьем лице»)
никому не присвоены.

На реальном созвоне «Оперконтур» (52 мин) обращений около 17. Но одного и того же человека диаризация делит на
2–3 «спикера», поэтому голоса расходятся (Даня: 2.0 / 2.4 / 2.0), и детектор честно оставляет «Спикер N».
До фильтров он ошибочно называл спикеров «Задача» и «Например»: ASR иногда пишет обычные слова с заглавной.
Сейчас слово, хоть раз написанное со строчной, именем не считается.

## Число спикеров в режиме «Авто»

Жалоба из ручных проверок: короткая запись двух человек («Привет, Максим.» / «Привет, Никита.», 4 с) давала
**1 спикера** — каждый голос звучал < 3 с, и правило «маленький кластер = шум» присоединяло его к соседу.
А 52-минутный созвон «Оперконтур», где на самом деле 6 участников, делился на 8 (Python-прототип: 10).

Что изменили (см. `docs/ARCHITECTURE.md`, шаг 4): маленький кластер сливается с соседом, только если похож на него
по голосу (косинус ≥ 0.4) или совсем крошечный; раздробленные голоса длинного созвона сливаются при косинусе
центроидов ≥ 0.9. Подбор — `tools/eval/cluster_sweep.py` (эмбеддинги считаются один раз и кэшируются),
короткие тесты — `tools/eval/make_short_tests.py`.

| Файл | Эталон | Было | Стало | DER было → стало |
|---|---|---|---|---|
| piper_2spk / 3spk / 4spk | 2 / 3 / 4 | верно | верно | 4.01 / 5.27 / 5.04 — без изменений |
| piper_fast / piper_noisy / dialog1 | 3 / 3 / 3 | верно | верно | 14.77 / 5.80 / 6.22 — без изменений |
| short_2v_mf (мужчина + женщина, 4 с) | 2 | **1** | 2 | 77.0 → 17.6 |
| short_2v_mm (два мужчины, 4 с) | 2 | **1** | 2 | 90.8 → 26.6 |
| short_2v_mm2 (вторая фраза 0.6 с) | 2 | **1** | 2 | 69.2 → 19.4 |
| short_3t_mf (3 реплики) | 2 | **1** | 2 | 82.5 → 21.9 |
| mono_* (3 монолога по 22–26 с) | 1 | 1 | 1 | без изменений |
| Запись с микрофона «Привет, Максим / Никита» | 2 | **1** | 2 | эталона нет |
| Реальные монологи с микрофона (1 и 32 с) | 1 | 1 | 1 | — |
| «Оперконтур», 52 мин | 6 | **8** (прототип 10) | **6** (прототип) / **7** (телефон) | эталона разметки нет |

Устойчивость на «Оперконтуре»: если выбросить случайные 10 % кусков речи (10 раз), получается 5–7 спикеров.
Граница тонкая: порог слияния 0.89 → 5 спикеров, 0.90 → 6, 0.92 → 8. Полный прогон в приложении на эмуляторе
(свои VAD, ASR и эмбеддинги на устройстве, 15 мин обработки) дал **7** — в пределах ±1. Под одну запись порог
не подгоняли, чтобы не переобучиться; если число участников известно, его лучше задать вручную.
Остаточный DER коротких клипов — границы фраз, а не путаница спикеров. Цифры — Python-прототип; Kotlin-код даёт ту же
разметку на тех же эмбеддингах (сверено на всех 19 файлах).

## Ручные проверки

| Сценарий | Результат |
|---|---|
| Живая запись с микрофона, 32 с, 1 человек | весь текст распознан, 1 спикер |
| Записи с одним говорящим (порог AHC 0.50–0.60) | не делятся на нескольких спикеров |
| Крик «Вась, Вась, Вась» (короткий, громкий) | ловится при пороге VAD 0.4 (при 0.5 терялся) → выбран 0.4 |
| Падение LLM (эмулятор Mac M4/M5 без `arm64.nosme`) | приложение и расшифровка целы, показывается понятная ошибка |
| **Release-APK** (R8, как у экспертов): импорт → расшифровка → конспект | dialog1: те же WER 4.84 % / DER 6.22 %, что у debug; 36 с аудио → 4.5 с; конспект готов, падений нет |
| Длинная запись: созвон 52 мин, WebM (VP8 + Opus 48 кГц stereo, 97 МБ) | обработан целиком: 839 реплик, 7274 слова, 8 спикеров. До исправления — OutOfMemory (декодер копил весь файл в 48 кГц, 600 МБ); теперь ресемплинг в 16 кГц на лету, ~200 МБ. На эмуляторе под App Nap 24 мин (декодирование Opus 14.7 мин, распознавание 5.7 мин, диаризация 3.5 мин) |
| **Часы → телефон, поток** (эмуляторы Wear OS 5 + Android 15, отладочный мост с тем же протоколом) | dialog1 (36 с) с часов: телефон сам открыл живой экран, текст по ходу; после «Стоп» получено ровно 578 692 сэмпла из 578 692, ACK через 0.5 с; полная расшифровка — WER 4.84 %, DER 6.22 %, 3 спикера из 3 — ровно как у импорта файла |
| **Часы без телефона** | запись 4 с → «на часах», файл в очереди («Не отправлено: 1»); связь вернулась → отправлен сам через 12 с, на телефоне ровно одна новая запись; повтор той же сессии — ACK без дубля |
| Release-сборки (R8) телефона и часов | обе без разрешения `INTERNET`; метка `glagol_phone` для поиска телефона сохраняется при сжатии ресурсов |
| Экспорт JSON | схема ТЗ: ключ `transcript`, `speaker_id` — строка `speaker_N`, `start_ms`/`end_ms` — целые, `text` — строка |

## Как повторить

```bash
scripts/download_models.sh                    # модели и AAR (один раз)
.cache/venv/bin/python -I tools/eval/make_piper_dialogs.py   # тестовый набор в .cache/test
scripts/dev_install.sh                        # debug-APK на устройство/эмулятор
tools/eval/device_eval.sh piper_2spk piper_3spk piper_4spk piper_fast piper_noisy.m4a dialog1
tools/eval/bench.sh                           # то же на Python-прототипе (без телефона)
```
